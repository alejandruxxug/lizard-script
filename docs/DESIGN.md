# lizard-script: design document

**Team:** Alejandro Urrego Giraldo, Maria José Sosa Fernández, Samuel Buelvas Cabrales. Compilers, Universidad EIA, 2026.

lizard-script is a small dynamically typed language with integers, booleans, strings, arrays, hashes and first-class functions. Full details are in [GRAMMAR.md](GRAMMAR.md) (syntax) and [SEMANTICS.md](SEMANTICS.md) (behavior).

## 1. Grammar (EBNF)

`{ x }` is zero or more, `[ x ]` is optional. `end` is a `;`, or nothing before a `}`, the end of the input or a line break.

```ebnf
program     = { statement } ;
statement   = "let" IDENT "=" expression end
            | "function" IDENT "(" [ params ] ")" block [ ";" ]
            | "return" [ expression ] end
            | "break" end
            | "continue" end
            | "try" block "catch" [ "(" IDENT ")" ] block [ ";" ]
            | "use" STRING [ "as" IDENT ] end              (* only at the top level of a file *)
            | ( ifExpr | whileExpr | forExpr ) [ ";" ]
            | expression end
            | ";" ;
block       = "{" { statement } "}" ;
params      = param { "," param } ;
param       = IDENT [ "=" expression ] ;

expression  = logicalOr [ ( "=" | "+=" | "-=" | "*=" | "/=" ) expression ] ;   (* right associative *)
logicalOr   = logicalAnd { "||" logicalAnd } ;
logicalAnd  = equality { "&&" equality } ;
equality    = comparison { ( "==" | "!=" | "===" | "!==" ) comparison } ;
comparison  = sum { ( "<" | ">" | "<=" | ">=" ) sum } ;
sum         = product { ( "+" | "-" ) product } ;
product     = prefix { ( "*" | "/" | "//" | "%" ) prefix } ;
prefix      = ( "-" | "!" ) prefix | power ;
power       = postfix [ "**" prefix ] ;                 (* right associative *)
postfix     = primary { "(" [ args ] ")" | "[" expression "]" } ;
primary     = IDENT | INT | FLOAT | STRING | COLOR | "true" | "false" | "(" expression ")"
            | "(" expression "," expression [ "," expression ] ")"
            | "[" [ args ] "]" | "{" [ pair { "," pair } [ "," ] ] "}"
            | "function" "(" [ params ] ")" block | ifExpr | whileExpr | forExpr ;
args        = expression { "," expression } ;
pair        = expression ":" expression ;
ifExpr      = "if" expression block { ( "elif" | "else" "if" ) expression block } [ "else" block ] ;
whileExpr   = "while" expression block ;
forExpr     = "for" "(" [ statement ] ";" [ expression ] ";" [ expression ] ")" block ;

IDENT = ( letter | "_" ) { letter | digit | "_" } ;   INT = digit { digit } ;   FLOAT = digit { digit } [ "." digit { digit } ] [ ( "e" | "E" ) [ "+" | "-" ] digit { digit } ] ;   (* with a "." or an exponent *)   unit = "deg" | "rad" | "turn" | "px" ;
STRING = '"' { any character but '"' } '"' ;        comment = "-~>" { any character but newline } ;
```

## 2. Architecture

```
source text ──> lexer ──> tokens ──> parser ──> AST ──> evaluator ──> values / output
                                                          │
                                       environments (scopes) + builtins
```

| Package | Responsibility |
| --- | --- |
| `token` | Token types, keywords, and each token's line and column. |
| `lexer` | Reads the text character by character and returns one token at a time. Always takes the longest operator (`===` before `==`). Unknown characters and unterminated strings become `ILLEGAL` tokens. |
| `ast` | The tree nodes. Each node keeps the token it comes from, and its span: where its text starts and ends (`node.Range()`). `Children` and `Inspect` walk a tree. |
| `parser` | A Pratt parser: one function per prefix form and one per infix operator, driven by a precedence table. It builds the AST and collects every syntax error with its position. |
| `object` | The runtime values (`Integer`, `String`, `Array`, `Hash`, `Function`, …) and `Environment`, a map of variables linked to the scope around it. |
| `evaluator` | `Eval(node, env)` walks the tree and returns a value. It also holds the builtins (`puts`, `len`, `str`, `int`, `push`, …). |
| `code` | The bytecode: opcodes, their encoding, and the compiled unit with its tables. |
| `compiler` | Turns the AST into bytecode for the VM, with the evaluator's rules for scopes and signals. |
| `vm` | `vm.Run(program, env)`: a stack VM that runs the bytecode, a second, faster engine with the same results. |
| `repl` | The interactive loop and `Run`, which runs a whole file (`RunVM` runs it on the VM, `RunFile` names it with its path, for its modules). They install the Terrarium first (the REPL without `window` and `pen`), and give it to modules too. |
| `terrarium` | The standard library: the modules `fs`, `os`, `time`, `json`, `img`, `clip`, `io`, `lizard`, and in `terrarium/window` and `terrarium/pen`, `window` and `pen`. See below and [TERRARIUM.md](TERRARIUM.md). |
| `bundle` | The format of a built program: a copy of `lizardscript` with a zip of the program's files and a trailer appended, and reading the `bundle:` paths of those files. |
| `tools/testrunner`, `tools/build` | `lizardscript test` (programs with a `.expected` file, and `*_bench.liz` benchmarks) and `lizardscript build` (one executable of a program folder, for any system). |
| `format`, `check` | `lizardscript fmt` (one layout for code, from the tokens and the spans of the tree; it checks that the tokens and the tree didn't change, see [STYLE.md](STYLE.md)) and `lizardscript check` (diagnostics without running: names resolved with the evaluator's scoping, modules read with `evaluator.FindModule`), also `lizard.check`. |
| `main.go` | `lizardscript` starts the REPL; `lizardscript file.liz [args]` runs a file; `lizardscript --vm file.liz [args]` runs it on the VM, and `--profile` also shows where the time went; `run`, `test`, `build`, `fmt`, `check` and `drive` are the commands above and the window automation. `os.args()` gives the args. A built program runs its own `main.liz`. |

**Errors.** Each kind of error is detected in its own stage and reported as `[line L, column C] <kind> error: <message>`:
- **Lexical:** the lexer turns a bad character into an `ILLEGAL` token, and the parser reports it as a lexical error.
- **Syntax:** the parser records the error, skips to the end of that statement (its line, under LEP 0001, with the brackets it opened) and carries on, so it reports every independent mistake at once, each with one error (`parser/recovery.go`). A program with any syntax error doesn't run at all.
- **Runtime:** the evaluator returns an `Error` value. It travels up the tree and stops the program, after any output the program had already printed.

**Control flow.** `return`, `break` and errors are values that travel up through `Eval`:
- a `ReturnValue` stops at the function call it belongs to;
- a `Break` stops at the innermost loop;
- an `Error` goes all the way up.

### The second engine: bytecode compiler and VM

`vm.Run(program, env)` has the contract of `evaluator.Eval(program, env)` and gives the same results: the same value, output, error messages and positions, steps and hook calls. It is several times faster on loops and calls (no environment map per scope, no allocation for small integers), for hosts that run a lot of code. The evaluator stays the default for the REPL and `Run`.

```
AST ──> compiler ──> bytecode (code.Unit) ──> vm ──> values / output
                                                │
                    frames + slots + cells, the host's environment, and the evaluator's operators and builtins
```

The structure follows the sequel of the course book (*Writing a Compiler in Go*), but lizard's rules win where they differ from Monkey's:
- **Resolved at compile time.** Each name a scope declares (lets, parameters, the catch name) gets a slot in its function's frame. The evaluator looks names up at run time in maps, so the compiler decides each read with the same answer: inside a function, a `let` has run before every read after it in its scope and not before any read earlier in it (each block, loop round and call starts its scope fresh), so an earlier read means the scope outside. A closure only knows whether the `let` had run when it was made: if not, its read checks the variable at run time and falls back to the next scope out while it is still unset. A local that a closure uses is a cell, new each time its scope starts, so closures share it by reference and each loop round gets its own.
- **Resolved at run time.** The program's own scope is the host's `env`, read and written by name, so globals added between runs are found, then the builtins, `null`, `math`, `text`, `list` and `hash`.
- **Signals.** `return`, `break` and `continue` are jumps that close the layers and trys they leave. An `if` or loop used as a value stops them and gets them as its value, and a statement whose value is one of those values acts like it, exactly as in the evaluator.
- **Fast paths.** Arithmetic and comparisons on integers and floats, point arithmetic (`p + q`, `p * n`), array indexing and dot access with a constant name (`a.b`, the hash key computed by the compiler, point coordinates read directly) run in the VM; anything they don't cover, including every error, goes to the evaluator. Small whole numbers are shared (`object.IntegerOf`, `object.FloatOf`), a point is one allocation (the point, its coordinates and their floats in one block), so is an array literal of two or three elements, a point of number literals is a constant, and a builtin gets its arguments lent from the VM's stack instead of a copy (the contract is on `object.BuiltinFunction`). A read of a global or a builtin remembers what it found and trusts it while `object.Environment.Version()` and `evaluator.LibraryResets()` stay the same; in a top-level loop that assigns a global every round it backs off, since every read misses there. A few instruction pairs are fused (`OpGetLocalField`, `OpGetCellField`, `OpGetNameField`), and a `let` in the middle of a block makes no `null` to drop.
- **Dot access remembers.** Each dot access in the code has its own `code.Field`, whose cache keeps the last hash it read, that hash's `Version()` and the value found; the next read of the same, unchanged hash is two comparisons instead of a map lookup. `object.Hash` counts its changes in `Version`, so a `Set` or `Delete` (from the program or the host) is seen at once. The cache keeps that one hash alive while the compiled unit lives.
- **Formulas.** An expression of two or more `+ - * /` (with maybe one `< > <= >=` on top) whose values are names, number literals and their dot accesses (`x * 1.5 + y`, `(p.x - a.x) * d.x`, `total += x * 2 - 1`) gets one `OpFormula` (`code.Formula`, `compiler/formulas.go`, `vm/formulas.go`): the VM reads the leaves and computes on Go numbers, so only the result is boxed and a comparison boxes nothing. The usual instructions of the expression follow it, and run when it can't give the value (a leaf that is not a number or fails to read, an operator that would fail): then the value and the error are exactly theirs. That is safe because reading a leaf runs no code of the program and changes nothing. A formula that gave up (points, strings) goes straight to its instructions for its next 32 runs.
- **Fewer signal checks.** An assignment whose value is an operator's result (`x = a + b`, `x += 1`) is never a `return`, `break` or `continue` value, so no `OpCheckSignal` follows it.
- **Interop points.** Everything but the fast paths calls the evaluator's own code through `evaluator/engines.go` (`Infix`, `Index`, `SetIndex`, `ApplyFunction`, `Builtin`, …), so messages can't drift apart. A VM closure is an `object.Callable`: it is a `FUNCTION`, prints its source, and the evaluator and `list.sort` call it; the VM calls the evaluator's functions and the builtins through `evaluator.ApplyFunction`. The step counter, `MaxSteps`, `Output`, the hooks and the call depth (10000 calls of both engines together) are shared.

### Profiling

`lizardscript --profile file.liz` runs the file on the VM and then prints, to the error output, the top 25 lizard functions by self time and by total time, with their call count and `name (file:line)` (`function@line` for an anonymous one, `program` for the code outside functions), and the top builtins. A host profiles part of its own work with `vm.StartProfile()` and `vm.StopProfile()`, which returns a `vm.Profile` (rows of name, source, line, calls, self and total; `Write(w)` prints the tables).

The profiler counts instead of sampling: every call the VM makes, to a closure, a builtin or a function of the evaluator, reads the clock when it starts and ends, so the counts are exact and short calls are not missed. Total time counts a recursive function once (only its outermost call); self time is total minus the calls it made. Each frame remembers the profile that counted it, so a return, an error or a `catch` that leaves frames ends their calls, and a profile started in the middle of a run ignores the frames from before. While it is off, a call costs one `nil` check more; while it is on, about two clock reads per call (a program of mostly builtin calls runs about 1.5 times slower).

### The Terrarium: the standard library

The Terrarium is how a program reaches the world outside it: files, the system, time, images, the clipboard, and a window with its input and pen pressure. With it a whole app can be written in lizard-script; the Go code only reaches the system, and what to draw, every pixel of it, is decided by the program. The full reference is [TERRARIUM.md](TERRARIUM.md).

```
host ──> terrarium.Install(env) ──> env: fs os time json img clip (+ window pen) ──> evaluator or vm
                │
     Go modules (one file each) + lizard-script modules (terrarium/lib/*.liz, run into env)
```

- **Modules are values, not syntax.** Each module is a HASH of builtins that `Install` defines in the program's environment, so `fs.read(path)` is plain dot access and a call, both engines run it unchanged, and a program's own `let fs = ...` hides it like any variable. They are made new for each install, so a change to one doesn't reach the next run.
- **Lizard-script first.** A module that needs no system access and no speed is written in lizard-script and embedded (`json` is). It runs in an environment of its own, so a program's variables never reach its code (a program's `let text = "x"` must not break `json.write`), and each of its functions is handed to the program as a builtin that calls it through `evaluator.ApplyFunction`, so its errors are reported at the program's call with the builtin's name in front, like a Go builtin's.
- **Opaque values.** An image or a window is an `object.Native{Kind, Value}`: type `NATIVE`, shown as `<image 640x480>`, equal only to itself. Only the builtins that know its kind look inside.
- **Drawing targets.** Images, windows and surfaces are drawn on the same way: `size`, `clear`, `fill`, `span`, `spans`, `blit`, the clip, the gradient spans, the blend layers and `composite` are one implementation (`terrarium/internal/canvas`) present in both modules, and each takes any target, so a drawing library can take any of them. A new target implements `pixels.Target`. The per-pixel work that would be too slow one pixel at a time in lizard-script (a gradient's color at each pixel, a blend mode's mix) is Go; what a gradient or a layer is stays the program's decision.
- **Surfaces and composing.** A window shows its buffer and, over it, its surfaces, each at a scale of its own; the frame is composed at the finest scale they share, and only in the rectangles that changed (the whole target unless the program declares smaller ones with `window.dirty`), each one on its own, so far-apart changes don't cost the space between.
- **Standard modules.** Big libraries written in lizard-script (the flower graphics family: `flower/lily2d`) are files in `terrarium/std/`, embedded by `std.go` into `evaluator.StandardModules`, and found by `use` after the program's folder and `$LIZARD_PATH`. They are not installed into every program like `json`, so a program that doesn't use one doesn't pay for parsing and running it at startup, and they are ordinary modules: live names, `as`, both engines, errors with their `std:/` source name.
- **Modules of the program.** `use "x"` (section 7, [LEP 0002](../proposals/0002-modules.md)) runs `x.liz` in a scope whose outer scope is a prelude with the same Terrarium (`evaluator.ModulePrelude`, set by `repl`), so a module's code reaches `fs` like the program's does but never the program's own variables.
- **Optional window.** `window` and `pen` need Ebitengine, so they live in their own package, which adds itself to `Install` from its `init` when a host imports it. A host with no screen calls `InstallCore` or doesn't import it, and doesn't link a window. `window.run` calls the program's `tick` through `evaluator.ApplyFunction`, like `list.sort` calls its comparison, so it works with functions of either engine. A headless window runs the same frames with no Ebitengine at all, so app tests and benchmarks run in `go test`.
- **Automation is opt-in and local.** A window is driven by another program only when it turns automation on; it listens on 127.0.0.1 with a random token in a per-process file only the user can read, and every command runs on the program's goroutine at the start of a frame, with its reply after that frame's `tick`, so a driver never sees half a frame and never races the program.
- **System differences** live in files with build tags (`sys_darwin.go`, `pen_windows.go`, ...). Nothing needs a C compiler, so the CLI builds for macOS, Windows and Linux from any of them.

## 3. Design decisions

- **A Pratt parser instead of one function per grammar level.** Precedence and associativity live in one table. Right associativity (`=`, `**`) comes from parsing the right side with one level less.
- **Desugaring.** `function f(x) {...}` builds the same tree as `let f = function(x) {...};`. An `elif` is an `if` inside the previous `else`. This keeps the AST and the evaluator small.
- **`if`, `while` and `for` are expressions.** An `if` gives the value of the branch that ran, so `let x = if (a) { 1 } else { 2 }` works. A loop gives `null`.
- **Block scopes.** Every block and every function call gets a new `Environment` linked to the one around it:
  - `let` creates a variable in the current scope, hiding outer ones with the same name;
  - `=` changes the closest existing variable, and assigning to an undeclared name is an error, which catches typos.
- **Errors can be caught, the host's limits cannot.** `try`/`catch` catches any runtime error, but the step limit and the stack overflows are marked `Uncatchable` on the error and go through every `try`: they exist to protect the host, and a program that could swallow them could loop forever in a `catch`.
- **Contextual words, no new keywords.** `try`, `catch` and `continue` are plain identifiers that the parser reads as statements only in the one shape that was invalid before (see section 7), so no program loses a variable by the name.
- **Closures.** A function value keeps the environment where it was created, so it can read and change those variables later.
- **Indentation for layers, braces for code.** Code blocks are closed by braces, and only `layer` bodies are closed by indentation, measured by the column of the first token of each statement with the positions the parser already has (no INDENT or DEDENT tokens). Mixing the two works: a layer inside a function body is measured from the `layer` word, not from the brace, and a tab counts as one column, so a file should not mix tabs and spaces in the same layer.
- **Two equalities.** `===` requires the same type and value. `==` first converts booleans and numeric strings to numbers, so `"5" == 5`. Arrays and hashes compare by content.
- **Integer arithmetic stays exact.** Floats (section 7) only appear when a float is written or produced by a float function, and any operation between two integers is the integer operation it always was.
  - `/` rounds towards zero and `//` rounds down. `%` pairs with `//`, so `a == (a // b) * b + a % b` always holds.
  - `**` with a negative exponent is an error, since the result wouldn't be an integer.
- **Floats never hold Infinity or NaN.** Any operation that would produce one (`10.0 ** 400`, `0.0 ** -1`, `math.sqrt(-1)`) is a runtime error, so a float is always a real number that prints and compares normally.
- **Truthiness.** `false`, `null`, `0`, `""`, `[]` and `{}` are false. `&&` and `||` short-circuit and always give a boolean.
- **Shared data.** Arrays and hashes are references: `let b = a` shares the same array, and functions can change their arguments.
- **Hash keys and order.** Keys keep their insertion order, so output is predictable. Only integers, booleans and strings can be keys (not floats, colors or points), and `1` and `"1"` are different keys.
- **No crashes on adversarial input.**
  - Printing and comparing values use an explicit stack instead of recursion, and detect values that contain themselves (shown as `[...]`).
  - The parser rejects programs nested more than 10000 levels.
  - The evaluator limits call depth (10000 calls) and total depth, so it reports a stack overflow instead of overflowing Go's own stack.
- **The REPL keeps reading lines while the input is unfinished**, like an open bracket or a trailing operator.

## 4. Known limitations

- Integer overflow wraps around, as in Go. Floats are 64-bit and never infinite or NaN (an operation that would produce one is an error).
- Syntax error recovery is a heuristic: when one random token of a valid program is deleted, doubled or replaced, about 0.04% of the broken programs give three or more errors (see "Better parser errors" in §7), and a second mistake on a line that already has an error shows up only after fixing the first.
- In the REPL, an `if` without `else` runs once the next line shows it is complete, or after an empty line.
- Nesting is limited to 10000 levels in the source, and recursion to 10000 calls.
- A layer is closed by indentation, so the REPL, which reads one line at a time, runs a `layer` typed there as an empty layer.
- In the REPL, a `try` block is run as soon as its line is complete, so the `catch` must start on the same line as the closing `}` (`} catch (e) {`); in a file it can be on the next one.
- `try` is a statement, not an expression: `let x = try { ... } catch { ... }` is a syntax error. Its value is only seen as the last statement of a function or block.
- A lone `continue` statement is a `continue`, so a variable of that name used as a lone statement (which did nothing) no longer does; outside a loop it is the syntax error `continue outside of a loop`, like `break`. As part of a larger expression (`continue + 1`) or a `let`, `continue` is still an ordinary name.
- Surprises that stay on purpose (they are written in the guide's "common mistakes"):
  - A negative index gives `null` on `a[i]` and `s[i]`, but counts from the end in `text.slice`, `text.find`, `text.code` and the `list` functions. The indexing operator never wraps, so a bug that goes below 0 shows up as `null` instead of silently reading the last element.
  - `"5" * 2` is `"55"` (`*` repeats a string) even though the text looks like a number, while `"5" + 5` is an error and `"5" == 5` is true. A string is never converted to a number by an arithmetic operator; only the loose `==` does it. Use `int("5")` to get the number.
  - Strings are compared byte by byte, not by alphabet: `"B" < "a"` is true, and `"é" < "z"` is false because the bytes of `é` are above those of `z`. This keeps comparison O(n) with no locale tables and gives the same order on every machine.
- Indexing a string is O(1) only after its first use, which costs one pass over the text (and memory for the characters of non-ASCII text); a `String` object caches that and is not safe to share between goroutines.
- An emoji written as a surrogate pair (`"\uD83D\uDE00"`) is an error: write the code point (`"\u{1F600}"`).
- An infinite loop runs forever unless the host sets `evaluator.MaxSteps`; in the REPL, stop it with Ctrl+C.
- The VM remembers what it found in a compiled unit (global reads, dot access, formulas that gave up), so one `code.Unit` must not run on two goroutines at once; compile it once per goroutine.
- The VM's global reads are fastest in functions: at the top of a program every variable is a global in the host's environment, read by name, so hot loops belong in functions (their variables are slots).
- A `use` is only allowed at the top level of a file, so a program can't catch a missing module with `try`; a host checks with `evaluator.FindModule`. The hash of `use "x" as m` is made when the module has run: a variable of the module read through it doesn't follow later changes (its functions do).
- An error raised inside a module's function shows the module's position, not the line of the program that called it: `lily2d.circle(w, "x", 4, #fff)` uncaught is `std:/flower/lily2d/check.liz: [line 7, column 8] runtime error: lily2d.circle: center must be a point ...`. The message names the call; a library can't yet point at its caller's line the way a Go builtin's error does.
- A built program (`lizardscript build`) is the `lizardscript` executable with the program appended after it. It runs on macOS, Windows and Linux, but on macOS the appended data makes `codesign --verify` report "main executable failed strict validation", and the file can't be re-signed or notarized as it is. A notarized release needs another way to carry the files (a Go program that embeds them, built with Go).
- `lizardscript test` runs the programs one after another in its own process, so a test that opens a real window shows it; `os.exit` in a test ends that test, not the runner.
- The VM has no Go recursion for lizard calls, so the evaluator's second stack limit (`the calls and the code inside them nest too deeply`, for up to 10000 calls whose bodies nest very deeply) never happens on it; only the 10000-call limit does. No test program reaches that limit.

## 5. Testing

`go test ./...` runs everything:
- unit tests for each package (lexer, parser, evaluator, REPL);
- the programs in `tests/`: 35 valid programs and 59 that must fail with a lexical, syntax or runtime error, each compared with its `.expected` output (the modules they use are in `modules/` folders next to them, which have no `.expected` file); `lizardscript test tests` runs the same programs;
- every program in `examples/`;
- the VM: every program of `tests/` and `examples/` also runs on it with the same `.expected` output, and a differential test runs each of the about 1400 programs in the evaluator's unit tests (valid and failing), plus hand-written corners of scopes, signals, try, layers and steps, on both engines, comparing output, value, error, step count and hook calls.

## 7. Extensions beyond the course design

Phases 1 to 4 follow the course's reference interpreter, and that foundation stays: the Go lexer, parser, AST and evaluator. Everything after commit `cc9dc0d` is added on top of it, so programs that worked before keep working the same way. Each extension is recorded here: what was added, why, and what it adds to the original tokens, AST, evaluator or builtins.

| Date | Extension | Why | What it adds to the course design |
| --- | --- | --- | --- |
| 2026-11-02 | String escapes | A string could not hold `"` or a line break on purpose. | Lexer only: inside a string, `\"`, `\\`, `\n` and `\t` become one character in the STRING literal; any other `\x` is an ILLEGAL token reported as `unknown escape \x in string`. No new token or AST node. No existing program or test had a backslash in a string. |
| 2026-11-02 | Dot access `a.b` | Reading and writing hash keys with `a["b"]` is noisy. | New token `DOT`, and a parser rule at `INDEX` precedence that builds the same `IndexExpression` with a string key as `a["b"]`, so the evaluator is untouched. A name must follow the dot (`expected a name after "."`). |

## 8. Future: unboxed values

This is a design note, not something built. Every value the VM handles is an `object.Object`, an interface: a number on the stack is a pointer to a heap `Integer` or `Float`. The shared small whole numbers, the point blocks and the formulas (section 2) take most of the allocations out of drawing code, but a float that is stored (`x = x + 0.25`) is still a new object, and in a real host workload Go's garbage collector is close to half of the CPU time.

**What it would take.** The VM's stack, locals, cells and constants would hold a tagged value instead of an interface:

```go
type Value struct {
	kind uint8   // integer, float, boolean, null, or object
	bits uint64  // the integer, the float's bits, the boolean
	obj  object.Object // only for kind object: strings, arrays, hashes, points, functions
}
```

- Every instruction reads and writes `Value`s; the fast paths work on `bits` directly, and a float result never allocates.
- Boxing happens at the edges, where a value leaves the VM: a builtin call, `evaluator.Infix` and the other interop points of `engines.go`, an element stored in an array or hash, a global written to the host's `object.Environment`. Unboxing happens where one comes in.
- Arrays and hashes still hold `object.Object`, so a float pushed into an array is boxed then; a typed array (all floats) would be a further step.

**Costs.**
- It is a rewrite of `vm/` and of the parts of `code` and `compiler` that hold values (constants, cells, closures' free variables), not an addition: every opcode handler changes.
- A `Value` is 32 bytes against an interface's 16, so the stack and the frames double in size, and copying them costs more; programs of strings, arrays and hashes would be slightly slower, not faster.
- Each interop point converts in both directions, so code that calls builtins in a tight loop (`math.sin(x)` for every pixel) boxes at every call unless the common builtins get unboxed versions.
- The differential tests must keep proving that both engines agree; boxing at the edges is exactly where an `===` on a float or a `-0.0` could slip.

**Benefits.** Integer and float loops would make no garbage at all, and the formulas would no longer be needed as a separate path; measured on the benchmarks, the allocations left in `FloatMath`, `Geometry` and `PointMath` are almost all boxed numbers and points. Before doing it, the cheaper steps are worth trying first: more formula shapes (unary minus, `%`, `//`), formulas over points (the vector of `vm/points.go` on Go numbers), and builtins like `math.sqrt` taking part in a formula.
