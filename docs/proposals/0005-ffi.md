# LEP 0005: Calling C libraries (`ffi`)

- **Author(s):** the lizard-script team
- **Status:** Draft <!-- Draft · Accepted · Rejected · Deferred · Final -->
- **Created:** 2026-11-03
- **Discussion:** to be opened as a pull request

## Summary

A new Terrarium module, `ffi`, lets a lizard-script program call functions of C libraries that are already on the system (or shipped with the program): `ffi.open` loads a library, `ffi.func(lib, name, args, ret)` makes a lizard function out of one of its C functions, with the C types of its arguments and result, and `ffi.alloc`, `ffi.read` and `ffi.write` handle memory that C reads and writes. It is built on purego, which the Terrarium already uses for pen pressure, so it needs no C compiler and the CLI still builds for every system from any of them. Because a wrong call can crash the process, `ffi` is **opt-in**: a program gets it only when it is run with `--allow-ffi`, and it never works inside `lizard.run`.

## Motivation

The Terrarium reaches the system through Go modules. A program that needs one more system library (a game controller, MIDI, a database, a system notification) needs a new Go module and a new `lizardscript`, built by someone who writes Go. "A whole app written in lizard-script alone" stops at the edge of what the Terrarium already has.

Today a program can find out which system it is on and name the library it would need, and stop there:

```
-~> What a program does today to pick a system file by name.
let names = {"macos": "libc.dylib", "linux": "libc.so.6", "windows": "msvcrt.dll"}
puts(os.platform(), names[os.platform()])
```

Today, with `./lizardscript` on macOS:

```
macos libc.dylib
```

```
puts(os.platform())
let libc = ffi.open("libc")
```

```
macos
[line 2, column 12] runtime error: identifier not found: ffi
```

The building block is already in the binary. `terrarium/pen/pen_darwin.go` loads AppKit with `purego.Dlopen` and calls Objective-C through `purego/objc`; `pen_windows.go` uses `syscall.NewCallback` for a window procedure. Each of those is Go written for one library. An FFI makes the same thing a few lines of lizard-script.

A quick check that purego can call functions whose types are only known at run time (what `ffi.func` needs, since the types come from the program): a Go program outside the repository built the function type with `reflect.FuncOf` from a list of types, bound it with `purego.RegisterFunc` and called `strlen("lizard")`, `cos(0.0)` and `abs(-7)` from libSystem, with `CGO_ENABLED=0` on macOS arm64 (Go 1.27, purego v0.11.0):

```
6
1
7
```

A second one made a comparison callback whose type was also built at run time (`reflect.MakeFunc`, then `purego.NewCallback`), sorted `[30, 10, 40, 20]` in `calloc` memory with `qsort`, and filled a block with `strncpy`, printing the first and last number and the text:

```
10 40
lizard
```

## The change

```
-~> with this LEP, run with: lizardscript --allow-ffi demo.liz
let libc = ffi.open({"macos": "/usr/lib/libSystem.B.dylib", "linux": "libc.so.6", "windows": "msvcrt.dll"})
let strlen = ffi.func(libc, "strlen", ["string"], "u64")
let abs = ffi.func(libc, "abs", ["i32"], "i32")
puts(strlen("lizard"), abs(-7))               -~> 6 7

-~> Memory C writes into: strncpy fills a block of 32 bytes.
let strncpy = ffi.func(libc, "strncpy", ["pointer", "string", "size"], "pointer")
let buf = ffi.alloc(32)
strncpy(buf, "lizard", 31)
puts(ffi.string(buf))                         -~> lizard
ffi.free(buf)

-~> A struct, and a callback: qsort calls a lizard function to compare.
let Vec = ffi.struct({"x": "f64", "y": "f64"})
puts(ffi.size(Vec))                           -~> 16
let qsort = ffi.func(libc, "qsort", ["pointer", "size", "size", "callback"], "void")
let nums = ffi.alloc(4 * 4)
for (let i = 0; i < 4; i += 1) { ffi.write(nums, i * 4, "i32", [30, 10, 40, 20][i]) }
let less = ffi.callback(function(a, b) { ffi.read(a, 0, "i32") - ffi.read(b, 0, "i32") }, ["pointer", "pointer"], "i32")
qsort(nums, 4, 4, less)
puts(ffi.read(nums, 0, "i32"), ffi.read(nums, 12, "i32"))   -~> 10 40
```

### Functions

| Function | Does |
|---|---|
| `ffi.open(path)`, `ffi.open(paths)` | Loads a library and gives it as a `NATIVE` of kind `library`. `path` is a file name the system's loader searches for (`"libc.so.6"`), or a full path. A hash picks the entry of `os.platform()` (`"macos"`, `"linux"`, `"windows"`), so one line works everywhere; a missing key is the error `ffi.open: no library for linux (the hash has macos, windows)`. The file is not checked with `fs.exists` first: on macOS the system libraries live in the loader's cache, not on disk (`/usr/lib/libSystem.B.dylib` doesn't exist as a file, and opens). |
| `ffi.func(lib, name, args, ret)` | The C function `name` of `lib` as a lizard function (a `BUILTIN` named `name`). `args` is an array of type names, `ret` one type name or `"void"`. Calling it checks and converts each argument, calls C, and converts the result. |
| `ffi.struct(fields)` | A struct type from a hash of field name to type, in order (`{"x": "f64", "y": "f64"}`). `ffi` works out the C padding and alignment (purego leaves that to the caller). A struct is passed and returned as a hash of its fields. |
| `ffi.size(type)` | The size in bytes of a type name or a struct. |
| `ffi.alloc(size)` | A block of `size` bytes of C memory, filled with zeros, as a `NATIVE` of kind `memory`. It is C memory (`malloc`), so C may keep a pointer to it. It lives until `ffi.free`. |
| `ffi.free(block)` | Frees a block. Using it after that, or freeing it twice, is an error, not a crash. |
| `ffi.read(at, offset, type)`, `ffi.write(at, offset, type, value)` | A value of a type (a number, a pointer, a struct) at `offset` bytes. On a block both check that it fits inside it; on a pointer (one C gave, like a callback's arguments) nothing can be checked, so it is the program's word. |
| `ffi.string(pointer, offset = 0)` | The NUL-terminated text at a pointer or block, copied into a lizard string. |
| `ffi.view(pointer, size)` | A block over memory that C gave (a pointer it returned). `ffi` can't know its size, so the program states it, and `ffi.free` doesn't free a view. |
| `ffi.callback(function, args, ret)` | A C function pointer that calls a lizard function (see Callbacks). |
| `ffi.null` | The null pointer. A function that returns a null pointer gives `null`. |

### Types

| Type name | C | Lizard value |
|---|---|---|
| `i8` `i16` `i32` `i64`, `u8` `u16` `u32` `u64` | the fixed-size integers | INTEGER. An argument that doesn't fit is an error (`abs: 3000000000 doesn't fit in an i32`), not a silent wrap. A `u64` result above the largest INTEGER is an error. |
| `int` `uint` `long` `size` | `int`, `unsigned`, `long`, `size_t` (sizes of the system) | INTEGER |
| `f32` `f64` | `float`, `double` | FLOAT; an INTEGER argument is converted |
| `bool` | `_Bool` | BOOLEAN |
| `string` | `const char *` | STRING, copied with a NUL at the end and valid only during the call. As a result, the text is copied into a lizard string; the C memory is not freed. |
| `pointer` | `void *`, any `T *` | a block, a pointer (`NATIVE` of kind `pointer`), or `null`. Pointers are not integers, so there is no pointer arithmetic outside `ffi.read`, `ffi.write` and `ffi.view`. |
| `callback` | a function pointer | a value of `ffi.callback` |
| a struct | a struct by value | a hash of its fields |
| `void` | (results only) | `null` |

C functions with a variable number of arguments (`printf`, `snprintf`) can't be called: on some systems (macOS on arm64) their extra arguments are passed in another way, which purego doesn't do. `ffi.func` can't tell from the name, so TERRARIUM.md says it.

An unknown type name is the error `ffi.func: unknown type "int32" (the types are i8, i16, ...)`, when `ffi.func` runs, not at the call.

### Callbacks

`ffi.callback(f, args, ret)` makes a C function pointer that, when C calls it, converts the arguments, calls `f` on the program's engine (through `evaluator.ApplyFunction`, like `list.sort`'s comparison) and converts what it returns.

- **Only during a call.** A callback runs `f` only while the program is inside an `ffi` call (qsort calling its comparison, a library walking a list). The program is waiting in that call, so no other lizard code runs at the same time, even if C calls back from another thread. A callback that C calls at any other moment (a library's background thread, later) doesn't run `f`: it returns zero, and the program's next `ffi` call fails with `ffi: a callback was called after its call ended`. The interpreter is not safe to run on two threads at once, so this is the line that keeps it safe.
- **An error in `f`** stops the C call as soon as the callback returns (it returns zero to C) and becomes the error of the `ffi` call, positioned like `list.sort`'s: the call, then the error inside `f`.
- **A limited number.** purego can make about 2000 callbacks on Unix and 1024 on Windows, and never frees them, so `ffi.callback` should be called once, at the top of a program, not in a loop. Past the limit it is an error. Callbacks take numbers and pointers, not structs by value (purego doesn't support those in callbacks).

### Library names on each system

The same C library has a different file name on each system, and on Linux often a version number: `libc.so.6`, `libm.so.6`, `libSDL2-2.0.so.0`. `ffi.open` takes the hash by platform so a program says it once, and the loader of each system does the searching (`DYLD_LIBRARY_PATH` and the dyld cache on macOS, `LD_LIBRARY_PATH` and `ldconfig` on Linux, the program's folder and `PATH` on Windows). A library shipped next to the program is found with `fs.join(os.program_dir(), "lib/libfoo.dylib")`.

### Safety

A C function trusts its caller. A wrong type list, a block freed too early or a pointer from the wrong place can crash the whole process, and a crash is not a runtime error: `try` can't catch it, and the window closes with no message. So:

- **Opt-in.** `ffi` is not in the Terrarium by default. `lizardscript --allow-ffi file.liz` (also `run`, `test` and `build`, where the built program remembers it) installs it. Without the flag the name `ffi` is still a module, so the message helps, but every function is the error `ffi is off: run the program with lizardscript --allow-ffi`. A host that embeds the interpreter imports `github.com/alejandruxxug/lizard-script/terrarium/ffi` and calls `ffi.Install(env)` itself; `terrarium.Install` never does.
- **Never inside `lizard.run`.** A sandbox only has what its `globals` give, but a program could pass `ffi`, or a function that calls it, in `globals` (passing `fs` works today: `lizard.run("puts(type(fs))", {"globals": {"fs": fs}})` prints `HASH`). So every `ffi` function checks whether it runs inside a `lizard.run`, and fails there with `ffi can't be used inside lizard.run`, whichever way it got in. The hooks of `lizard.run` run as the calling program, so they may use it.
- **Checked where it can be.** Integers that don't fit, reads and writes outside a block, a freed block, a null pointer passed as a block, an unknown type: all are runtime errors with the function's name in front, like every Terrarium error. What can't be checked is whether the type list matches the C function; TERRARIUM.md says so in its first line on `ffi`.
- **A module that wraps a C library** (`use "gamepad"`) still needs the program run with `--allow-ffi`. It can check `ffi.enabled()` and give its own message.

### Moving `window` and `pen` onto it

The question is whether the Terrarium's own system code could be written in lizard-script on top of `ffi`. The answer for now is no, and `ffi` doesn't need it:

- **`window`** is Ebitengine, a Go library, not a C one, and its loop owns the main thread. There is nothing in C to call.
- **`pen` on macOS** installs an `NSEvent` monitor whose handler is an Objective-C *block* (not a C function pointer) and calls `objc_msgSend` with a different signature for each message. Both could be done with `ffi.func(objc, "objc_msgSend", ...)` per signature and a block helper, but the handler runs inside Ebitengine's event loop, outside any `ffi` call, which the callback rule above forbids.
- **`pen` on Windows** subclasses the window with a window procedure, which Windows calls on every message, again outside any `ffi` call.

So `window` and `pen` stay in Go. What `ffi` adds is the libraries the Terrarium doesn't have, written as lizard modules, and a way to try one in lizard-script before deciding it deserves a Go module. A later LEP could add `window.handle(w)` (the `NSWindow *` or `HWND`) so `ffi` code can call system functions on the program's own window, and could revisit the callback rule with a queue that `window.run` drains every frame.

## How other languages do it

| | Python `ctypes` | LuaJIT FFI | Deno FFI | **lizard-script** |
|---|---|---|---|---|
| Loading | `CDLL("libc.so.6")` | `ffi.load("c")` | `Deno.dlopen(path, symbols)` | `ffi.open(path or hash by platform)` |
| Describing a function | `f.argtypes = [c_int]`, `f.restype = c_int` | C declarations in `ffi.cdef[[ int abs(int); ]]`, parsed | `{abs: {parameters: ["i32"], result: "i32"}}` | `ffi.func(lib, "abs", ["i32"], "i32")` |
| Structs | `class P(Structure): _fields_ = [...]`, padding computed | C `struct` declarations | `{struct: ["f64", "f64"]}` | `ffi.struct({"x": "f64", "y": "f64"})`, padding computed, values are hashes |
| Memory | `create_string_buffer`, `cast`, pointers with arithmetic | `ffi.new("int[4]")`, cdata indexed like arrays, GC-managed | `Deno.UnsafePointer`, `UnsafePointerView`, typed arrays | blocks with bounds checks, `ffi.view` for C's memory, no pointer arithmetic |
| Callbacks | `CFUNCTYPE(...)(f)` | Lua functions cast to function pointers, limited in number | `Deno.UnsafeCallback`, can be thread-safe | `ffi.callback`, only during a call |
| Permission | none: any program can | none | `--allow-ffi` | `--allow-ffi`, never in `lizard.run` |
| Speed | slow (conversions at every call) | as fast as C (the JIT compiles the call) | fast (calls compiled once per signature) | a reflection call through purego, about the cost of a builtin call |

lizard-script is closest to Deno: type names as strings, one description per function, a permission flag on the command line. Its structs are computed like ctypes'. It doesn't parse C declarations as LuaJIT does: that would need a C parser, and lizard-script code then contains C code. It is the most conservative of the four about memory (no pointer arithmetic, checked blocks) and threads, because a crash in a learner's program should be as rare as it can be.

## What breaks

Nothing. `ffi` was `identifier not found` (run above), and a program that defines its own `ffi` hides the module, like any Terrarium name. Without `--allow-ffi` nothing reaches C. No `.liz` file in this repository uses the name `ffi`. No token, AST node, evaluator or VM change.

## Implementation

- **New package `terrarium/ffi`**, not registered by `terrarium.Install`: `ffi.go` (the module), `types.go` (type names, conversions, struct layout), `memory.go` (blocks, views, read and write), `callback.go` (callbacks, the "only during a call" flag), `open_unix.go` (`purego.Dlopen`, `purego.Dlsym`) and `open_windows.go` (`windows.LoadLibrary`, `GetProcAddress`; purego's `Dlopen` doesn't exist on Windows, but `RegisterFunc` does). A function is bound once, in `ffi.func`: the Go function type is built with `reflect.FuncOf` from the type names and bound with `purego.RegisterFunc`, as in the check above; each call converts the arguments and calls it.
- **Terrarium:** `terrarium.Sandboxed()`, true inside `lizard.run` (a counter in `lizard_run.go`), which `ffi` checks.
- **`main.go`, `tools/build`, `bundle`:** the `--allow-ffi` flag; a built program records it in its trailer. A library inside a built program (`bundle:` paths) can't be loaded from the zip; `ffi.open` would copy it to a temporary file first (see open questions).
- **Both engines** run it unchanged: `ffi` is a module of builtins, and callbacks call the program's function through `evaluator.ApplyFunction`.
- **Tests:** a table of programs in `terrarium/ffi`, calling the C library of each system (libc on macOS and Linux, msvcrt on Windows): integers, floats, strings, structs, blocks, `qsort` with a callback, and every error (bounds, a freed block, an unknown type, `ffi` off, `ffi` inside `lizard.run`). The CI runs them on the three systems.
- **Rough size:** about the size of `img` (a module with its own value kinds), with no change outside the Terrarium and the command line.

## Alternatives

- **Do nothing.** Each new library is a Go module in the Terrarium. Safe and fast, but only for people who write Go and rebuild `lizardscript`.
- **cgo.** The standard way to call C from Go, but it needs a C compiler on every machine that builds `lizardscript`, and it ends the cross builds of `lizardscript build --os`. DESIGN.md: "Nothing needs a C compiler".
- **C declarations, as in LuaJIT** (`ffi.cdef("int abs(int);")`). Lets a program paste a header, but needs a C parser in the Terrarium, and puts C in lizard code.
- **A helper process** that loads the library and answers over a pipe. A crash would not kill the program, but every call would cost a round trip, and C memory and callbacks can't cross a process.
- **WebAssembly modules** (with a pure-Go runtime such as wazero). Sandboxed and portable, but they can't reach the system libraries that are the reason for an FFI.

## Open questions

- Should `--allow-ffi` be the only switch, or should a program also say it in its own text (a `-~> uses ffi` line, a line in `bundle.txt`), so `lizardscript test` and a reader see it without running it?
- Callbacks from other threads (an audio library) are refused. Should a later step queue them, for `window.run` to drain once a frame?
- Should a built program be able to carry its own libraries inside the bundle (copied to a temporary folder when opened), or must they be files next to it? macOS signing (DESIGN.md, Known limitations) makes the first one harder.
- `u64` results above the largest INTEGER are an error. Is that right for hashes and handles, which use all 64 bits? A `"u64bits"` type that wraps on purpose would fix it.
- Should an image (`img.new`) or a surface be passable as a `pointer`, so C can fill its pixels directly? It is Go memory, which C may use only during the call (the cgo rules).
- Which purego limits should TERRARIUM.md list: structs by value only on 64-bit systems, no structs in callbacks, the number of callbacks?
